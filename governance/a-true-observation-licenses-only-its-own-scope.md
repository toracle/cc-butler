An observation can be perfectly accurate and still not support the conclusion drawn from it. The recurring failure is not sloppy looking — the looking is usually fine — it is that **the conclusion covers more ground than the evidence does**, and nothing in the moment flags the gap. A true premise makes a false conclusion feel verified.

Three forms, all seen on 2026-08-06 within a few hours of each other, across three different sessions:

**1. Exoneration mistaken for diagnosis.** The steward investigated whether jarvice#1567 caused the CI formatter drift blocking every PR, established with three solid data points that it did **not**, and stopped there. Ruling out a suspect answers "was it this?" — it does not answer "then what was it?", and only the second question ends the outage. The real cause (our own #1562 merging two unformatted files) was one `git log` away and went unfound for hours while the fleet kept merging conditionally past red checks.

**2. A subset searched, a universe concluded.** Hours later the butler checked the ~30 **open** PRs for a formatter fix, found none, and concluded no fix existed — then dispatched a worker to build one. PR #1574 had already been merged and closed, which is precisely why it was not in the open set. The observation was true of the set examined; the conclusion was about all PRs.

**3. A narrow denial read as a broad malfunction.** A worker's `gh pr merge` was blocked, and it reported the permission classifier as non-deterministic, noting an identical command had worked that morning. It was not identical: this run carried `--delete-branch`, which the earlier one did not. The classifier was denying the destructive branch-deletion side effect while permitting the merge itself — entirely deterministic. Re-running the bare form succeeded on the first try. Note this instance's target: the false conclusion was about a **tool** rather than a code artifact, and it took the shape of "the control is unreliable," which is the most expensive possible misreading of a working safety control.

**4. A filtered view reported as the artifact (2026-08-07, steward).** Investigating whether staging deploys hide per-tenant migration failures, the steward ran `gh run view --log | grep -iE "migrat|tenant|alembic"` over the migration stage, got four lines back, and relayed to the worker that the stage emits **"정확히 4줄"** — quoting them as the stage's complete output.

The stage emits five. The missing line — `⏳ Waiting for it to complete (no fixed timeout — Fargate tasks aren't bound by Lambda's 15-minute cap)...` — contains none of the grep's terms, so the filter dropped it. **The filter was the steward's own, and its output was then presented as the artifact.**

The worker re-derived it from an unfiltered read and corrected the steward, adding: *"steward relay는 여전히 재확인 없이는 못 믿는다는 근거가 하나 더 쌓였습니다."* That is the correct response and the correct lesson to draw — see [[a-channel-that-carries-authority-must-be-verifiable-by-the-receiver]].

Two things make this instance worth recording despite the conclusion surviving (there genuinely is no `MIGRATION_RESULT` in CI logs). First, **the word doing the damage was the precision word.** "정확히 / exactly" converts a filtered sample into a completeness claim, and it is exactly the word one reaches for when trying to be rigorous. Second, **it happened inside a message arguing for exact evidence** — the steward was upgrading the worker's code-reading inference to an observation, and mis-cited the observation while doing so. Rigor about someone else's evidence is not rigor about your own.

**5. A synthesis stronger than any of its sources (2026-08-08, steward).** Three mutually-blind tracks verified jarvice PR #1582. Each reported something true and narrow about the MSSQL validator: code-review found the regex evadable but sqlglot catching every variant; exploratory found ~28 evasion attempts all caught downstream; verify-first found one comment-injection bypass masked by "parser accident, not design." Synthesizing them, the steward wrote that sqlglot was *"a load-bearing security dependency, unpinned and uncanaried"* — and was one call away from sending it to 정수님 as the headline finding.

Checked against the artifact first. Both halves were wrong. `uv.lock` pins sqlglot to 30.12.0 (only `pyproject.toml` carries the open `>=30.12.0`), and a canary **exists**: the tests monkeypatch `sqlglot.parse` to explode if called, proving the regex fires *before* any parse. The author had already anticipated the exact risk being alleged against them.

What makes this distinct from #4 is that **no filter was involved and every source was correctly attributed.** Three true reports went in; a claim none of them made came out. "Uncanaried" appears in no track's findings — compression generated it, because a single vivid phrase is what synthesis rewards. The accurate version is narrower and less quotable: *the canary is real but scoped to the literal strings someone thought to list, and the comment-injection bypass routes around it entirely.* Note that this sharper claim is also the more useful one — it says exactly where to look.

The steward's job is synthesis, which makes this the failure mode of the role itself: [[merging-agent-results-must-keep-per-claim-provenance]] guards *whose* observation each claim is, and every attribution here was correct. Aggregation needs its own guard — N observations jointly license only the ground they jointly cover, never a rounder-sounding superset.

**6. One file reviewed, a two-file deliverable certified (2026-08-08, steward).** A worker prepared a staging-census "script": a `.sh` that opens an SSM tunnel, and a `.sql` it feeds to `psql`. The steward read the `.sh` closely and caught two real defects before it could reach 정수님 — a `sed` URL rewrite that silently truncates passwords containing `@`, and a local-port collision that would attach `psql` to a *local* database and return "table not found," **which is shaped exactly like the answer being looked for.** Good catches.

Then the steward reported to butler: *"읽기 전용 census SQL(DDL 없음)"* — never having opened the `.sql`. Butler read it. Line 1:

```sql
DROP TABLE IF EXISTS tmp_alembic_census;
```

Unqualified. In a fresh `psql` session no temp schema exists yet, so the name resolves against **`public`**, not `pg_temp`. Had a real table carried that name in staging, the "read-only" census would have dropped it — by 정수님's own hand, on the steward's assurance that it was safe.

Two things generalize. First, **the unit of delivery is not the unit of review.** The two files arrived as one thing called "the script," and inspecting one carried over to a claim about both; nothing in the moment marked the second file as unexamined. Second, **finding defects is what made this feel finished.** Two real catches produced the sensation of a completed review, and that sensation covered a file never opened — the near neighbour of [[fixing-one-instrument-flaw-does-not-validate-the-instrument]], but about *review coverage* rather than a repaired instrument.

Note where this one was heading. The claim was not an analysis but a **safety assurance authorizing a human to run a destructive-capable command**, three relay hops from the person who would type it. "Low probability" and "read-only" are different sentences, and only one of them is what you say to someone before they press enter.

**7. A truncated view reported as the artifact (2026-08-08, butler).** Asked whether the scheduler dispatcher was actually wired to anything, butler grepped the repo for `schedule_dispatch` and reported that only tests and a docstring matched — **"no EventBridge rule, no CDK wiring"** — and added the inference that the wiring must therefore live in another repo. Both halves were false: `infra/cdk/stacks/scheduler-stack.ts` defines `functionName: jarvice-${env}-schedule_dispatch` with its handler, right there.

The steward misdiagnosed the cause as a too-narrow filter (`.py` but not `.ts`). Butler re-ran its own command and produced the real one: the `--include="*.ts"` **was** present. There were **28 matches**; its trailing `head -20` cut at twenty, and the first twenty all sat under `backend/`, so the CDK file fell at position 24 and never reached the screen.

So this is case 4's sibling with a different instrument: not a filter that dropped a line by content, but a **cap that dropped the tail by position**. And the distinction is load-bearing, because the two diagnoses imply opposite fixes — *"remember to include `.ts`"* would not have prevented this at all.

The tell was sitting in the output. **A capped query that returns exactly the cap is reporting the instrument's limit, not the world's** — see [[suspiciously-uniform-is-the-instruments-fingerprint]]. Twenty results from `head -20` is never a finding. Butler caught this in itself and named it against the same standard it had been holding others to all night.

**8. An empty result from a query that never worked (2026-08-08, steward, hours after case 7).** Deciding whether a guard-misreads-`public` hypothesis could fire at all, the steward set out to enumerate every table the `public` migration branch creates, and ran `grep -rhoP 'create_table\(\s*"\K[a-z_]+' public/`. It returned **nothing**.

Taken at face value that reads *"the `public` branch creates no tables"* — which would have inverted the entire argument then being built. The steward was about to tell butler, who was about to tell 정수님, that the guarded set and the `public` set were disjoint; an empty `public` set makes that trivially and wrongly true. The actual cause was the steward's own pattern: `grep -P` does not span newlines without `-z`, and the calls are formatted `op.create_table(\n    "auth",`. Re-run multiline-safe, it returned **21 tables**.

**This is case 7's sibling and the more dangerous one, because it has no tell.** Case 7 announced itself — exactly-twenty-from-`head -20` is a fingerprint you can learn to see. **Empty has no fingerprint at all: "nothing exists" and "my query is broken" render identically.** And it lands on the strongest claim in the vocabulary, since absence is what a single unopened line can falsify.

The defense is mechanical and was already in play elsewhere in the same investigation. The steward had just required the worker's reproduction to run **A0 first — prove the harness can produce a positive before trusting a negative** — and then skipped exactly that step for its own search. **A query that returns nothing must first be shown capable of returning something.** It is [[a-test-that-cannot-fail-is-not-evidence]] applied to search: point the same pattern at a case you know is present, and only then believe the zero.

**9. The data verified, the surface that consumes it never opened (2026-08-10, dealmatch worker).** A worker loaded 2026 construction-capability data into staging and verified it thoroughly: row-level diffs down to zero, records read back through `list_constructor_ability`. Every check passed, and it reported the reflection complete.

정수님 opened the page in a browser. **500.**

The upload had introduced rows where `prev_rank` is null — constructors that rose from outside last year's TOP100 — and `render_number_diff_arrow` calls `int(prev_rank)` unguarded. Because it is a `simple_tag`, the exception propagates out of the whole render: **one bad row takes down the entire page**, on a route with no `LoginRequiredMixin` and no auth middleware. The queryset filter that might have saved it, `exclude_no_data()`, screens `rank` and `valuation_amount` and not `prev_rank`.

The worker's own diagnosis is the cleanest statement of this whole file: *"`list_constructor_ability`로 읽은 건 데이터가 맞다는 증명이지 페이지가 뜬다는 증명이 아닙니다"* — reading it back proves the data is right, not that the page renders.

**This is the layer-crossing form, and it is the one the other eight do not cover.** Cases 2, 4, 7, 8 are all about *scope within one layer* — a subset of PRs, a filtered log, a capped grep. Here the observation was complete and correct at its layer (storage) and simply said nothing about the next one (rendering). No wider search, no uncapped query, no positive control would have caught it, because **nothing was wrong with the looking.** The data really was correct. The gap is that "the data is correct" and "the feature works" are claims about different systems, and reflection-type work makes them feel like one claim.

What makes it expensive is the second-order effect. This worker had also written the reasoning behind a release option currently in front of 정수님 — *"blockers 1–3 only bind DoD2; DoD1 is possible in principle without a release"* — and that sentence was **false for exactly this reason**. Production was returning 200 not because the code was sound but because the 2026 data had not landed yet; the last shipped tag carries the same unguarded call. Shipping DoD1 without the fix would have 500'd a public page for every user. **A verification gap at one layer had propagated into a release decision at another**, wearing the authority of "verified in staging."

Two things the worker did right, and they are the reason this is recoverable: it found the falsified premise itself and reported that its own stated reasoning was wrong, and it **annotated the false sentence rather than deleting it**, so why it was wrong survives.

**The sharpest point came from the worker afterward, and it closes off the obvious wrong lesson.** The null here was **not bad data.** A constructor with no `prev_rank` is a legitimate new entrant — genuinely absent last year, correctly represented as absent. There was nothing at the data layer to detect, so **no amount of stricter data validation could ever have caught this.** Tightening row-level checks, adding a null audit, diffing harder — all of it would have passed, correctly, forever. That is what makes "verify the data more carefully" the wrong response and "open the consuming surface once" the only one.

**And the steward committed case 2 while documenting case 9.** Verifying the worker's report, it checked whether the unguarded call was live by examining the production tag `v1.270.0` and `origin/staging` — two refs — and wrote the conclusion as *"the code actually running is vulnerable."* It never opened `origin/master`. The worker did, ran `grep -c` across all three, got 1/1/1, and reported master as *"what you didn't look at."* The conclusion held, so nothing generated friction; had master diverged, a false claim would have travelled upward inside an escalation whose entire purpose was correcting someone else's premise.

Two refs agreeing is not evidence about a third — it is the subset-searched-universe-concluded shape, in the specific and easy-to-miss costume of **branch/environment coverage**. The worker was explicit that its own catch was not method: *"운이 좋았습니다 — 두 ref가 같으면 세 번째도 같을 거라고 넘겼을 수 있었는데"*, saved only by a habit built from being burned on master/staging divergence earlier in the same session. A guard that depends on someone's recent scar tissue is not a guard.

The same worker also refused the tempting fix. Told that the queryset filter `exclude_no_data()` screens `rank` and `valuation_amount` but not `prev_rank`, it declined to add `prev_rank` to the filter: **screening it would delete a real constructor from the table.** Null is valid input the view must tolerate, not contamination to be filtered out — so the fix belongs in the consumer, not the query. Note the shape of the trap: a missing filter *looks* like the defect, and "make the data uniform" is always the cheaper-looking repair than "make the consumer robust." It buys a green page by silently dropping rows.

**10. The surface was opened with the eyes, and the eye is itself a filtered read (2026-08-10, dealmatch worker + steward).** The direct sequel to case 9, in the same investigation. Having been burned by never opening the page, the worker did exactly what item 13 prescribes: browsed staging, captured a screenshot, confirmed the previously-fatal row now renders with its designed `-` placeholder. **A genuine pass, correctly obtained** — and it also cleared the trap that mattered, since "row vanished but page returns 200" would have meant the crash was bought by deleting a real record.

Two things the eye could not see.

The worker found the first itself. It had written into the pass-criteria document that the neighbouring cell would be *blank* — an inference from reading the template, never measured. The cell renders literal **`None`**. Its own account: *"코드를 읽고 추론한 걸 실측 없이 사실처럼 써버렸다"*. **An inference laundered into a Definition of Done is worse than an inference in a report**, because the DoD is the yardstick every later check is measured against — a wrong expectation there does not merely mislead once, it certifies the wrong thing repeatedly, and quietly.

The steward found the second by cross-checking the claim mechanically — fetching the HTML rather than looking at the picture. The `None` leak was not 8 visible cells but **47 occurrences**: 39 of them inside `href` attributes of external credit-rating links (`kiscd=None`, `COMP_CD=None`, `cmpCd=None`) across a *different* set of rows, from a *different* nullable field. Those anchors render their text as `-`. **On screen they are indistinguishable from correct.** No screenshot, no visual inspection, no amount of careful looking could ever surface them — the defect lives in what the page hands to the *next* system, not in what it paints for a human. The same read also showed `<article>` 200 times against `</article>` once: every row emitting a malformed element, from the very template the fix had just edited, and equally invisible to the eye.

**Then the worker checked the steward's numbers instead of transcribing them, and two more things fell out.** First, the steward's *"11 rows have `None` hrefs"* was wrong: the query had actually filtered on `kiscd=None` alone, while the real predicate was *any of three* agency codes. Sixteen rows are affected; the five missing ones each had only a single agency blank, so they hide among the rows where all three are — and they would have survived a fix aimed at the visible cluster. **The steward wrote the conclusion wider than the predicate it ran**, in the same cross-check whose entire purpose was widening someone else's scope, which is case 2 committed by the person applying case 2.

Second, and more useful: **the worker counted the tag balance in the browser DOM first and got 200:201 — balanced.** The HTML parser had silently repaired the malformed markup. Only `curl` on the raw bytes shows 200:1. So the instrument that is *closer to the user* is the one that erases this defect: **anything read through a parser shows you what it managed to recover, not what was served.** A DOM inspection can never find this class of bug, no matter how carefully done.

**So item 13 has a floor, not a ceiling, in it.** "Open the consuming surface" is necessary and it is not sufficient, because **the rendered surface is not the last consumer.** It passes values onward — into URLs, data attributes, form values, downstream payloads, assistive technology — and the eye samples only the painted layer. Case 9's fix was *cross the layer*; case 10's is *do not assume the layer you crossed into is the final one, and do not verify it with an instrument that can only see part of it.* Where case 9 was a layer never opened, this is a layer opened with a tool that filters — which puts it back in this file's central shape, with the eye playing the role `grep` played in case 6.

**Why:** Each of these cost real time or nearly caused real harm — hours of conditional merging, a redundant dispatch that had to be recalled, (had it been believed) a standing distrust of a control that was functioning correctly, and in the fourth a verbatim quote that would have gone into a GitHub issue as evidence had the worker not re-read the source. In all four the person was being careful and reported honestly; honesty is what made them catchable. What was missing was a single explicit step between observing and concluding.

**How to apply:**

1. **After a negative result, say the next question out loud.** "It wasn't X" is a waypoint, never a destination. If an outage or defect is still live, the only terminal answer is what *is* causing it. Do not close, report, or move on from a pure exoneration.
2a. **Enumerate refs and environments before concluding across them.** "Is this live?" is a question about a *set* — every release tag, `master`, `staging`, `devel`, each deployed environment — and checking two of them proves two of them. Branches diverge; that is what they are for. Write the list first, check each, and say which ones you actually ran against. This is item 2 in the costume that hides best, because refs feel like one codebase rather than a set of them.

2. **Name the set you actually searched, in the same breath as the conclusion.** "No fix exists among the *open* PRs" is a claim you can check; "no fix exists" is not. Writing the qualifier makes the gap visible — most of these die on contact with their own scope statement. Closed/merged items, archived channels, and filtered defaults are where the answer hides precisely because they fell out of the default view.
3. **Diff what you ran against what you meant to run, before blaming the tool.** A blocked or failed command is evidence about that exact invocation — every flag included. Reproduce with the narrowest form that would satisfy the intent before concluding the tool is broken, flaky, or non-deterministic. See [[known-flaky-is-a-claim-not-a-diagnosis]], which is the same disease in the specific setting of test failures: a label that ends inquiry.
4. **Treat "the control is unreliable" as the highest-bar claim you can make.** It licenses working around a safety mechanism, so it needs stronger evidence than any other conclusion, not weaker. Narrowing the request is legitimate; switching mechanism to accomplish a just-denied action is circumvention. See [[relayed-authority-cannot-self-certify]].
5. **Expect this from good workers, and ask for the scope rather than the certainty.** All four instances came from careful operators reporting accurately. The correction is not "be more careful" — it is a habit of stating scope, which is cheap and mechanical. When a worker reports a negative finding, ask what set it covered before acting on it.
6. **Never quote an artifact from a filtered read.** `grep`/`sed`/`head`/`--jq` outputs are evidence about *what matched*, never about what the artifact contains. Before quoting anything verbatim — especially into an issue, a PR body, or a relay — re-read the region unfiltered (`sed -n '/start/,/end/p'` beats `grep` for this). If you must cite from a filter, cite it as one: *"grep for X matched these 4 lines"*, not *"the stage emits 4 lines."*
7. **Treat your own precision words as a trigger to re-check.** "정확히", "exactly", "the complete", "all of the" convert a sample into a census. When you are about to write one, that is the moment to go back to the unfiltered source — the instinct producing the word is the instinct that skipped the check.

8. **When merging several reports, check the merged sentence against a source — not against the other reports.** Synthesis rewards one vivid phrase, and the phrase routinely asserts more than any input did. Before a cross-source conclusion goes out, pick its strongest word and ask which report actually said it; if none did, you generated it, and it needs the artifact checked directly. Watch especially for absence words — "unpinned", "uncanaried", "untested", "undocumented" — since a claim that something *does not exist* is falsified by a single line in a file you have not opened, and is the cheapest of all claims to check.

    **The same trap fires when you summarize your own correct data, and there it has no seam to notice.** Case 10 produced a matched pair: the steward counted a narrow predicate and stated a wide one; the worker counted exactly right and then eyeballed its own per-row table into *"all five are kr-only"* when one row had two agencies blank. Different errors, one shape — **the numbers were fine and the sentence laid on top of them was not**, so no arithmetic check could reach either. The worker's diagnosis: *"데이터는 정확한데 그 위에 얹은 한 문장이 정확도를 잃은 겁니다."* Summary is a lossy operation performed by the same eye that just did the careful work, and it feels like reporting rather than like inference. So re-derive the summary sentence *from the table*, not from your memory of building it. And the reason this one was caught at all is worth keeping: the worker shipped the table alongside the claim, which is [[relayed-numbers-carry-decomposition]] — **a claim handed over with its decomposition can be checked by the recipient; a claim handed over as a sentence cannot.**

    **A third mechanism completed the set an hour later, and it is the quietest.** The butler told the human a pending release carried *"42 commits"*; the range actually held 49. Nothing was miscounted and nothing was blurred — **42 had been measured correctly the previous day**, and merges since had made it false while it sat in a summary being carried forward. So the three ways a number goes wrong here are: *counted a narrower predicate than you state* (steward), *summarized correct data loosely* (worker), and *quoted a measurement that has since decayed* (butler) — and **none of the three is reachable by re-checking the arithmetic**, which is the only check anyone instinctively runs. The defense differs per mechanism, but the stale one is the most insidious because the number was never wrong, merely old, so its author remembers verifying it and is right to. **Treat any figure describing mutable state as perishable: re-measure it at the moment it is used to decide, not at the moment it is first learned** — especially a figure about branch state, queue depth, or open items, all of which move while you are writing about them. Say when it was taken if you cannot re-take it.

    **A fourth instance the same afternoon exposed a gap in every defense above: the claim can hide inside an action.** A deploy sat queued behind a shared runner. The worker cancelled the stale runs it could see from a `--limit 4` listing, concluded it had cleared the queue, and moved on to suspecting the runner was offline — querying an org API that returns 403 either way. The blocker was a third run from the same dead branch, created 57 seconds earlier and therefore first in line. Cancelling it started the deploy instantly. **"I cancelled the runs I knew about" and "no runs remain" are different claims**, and the second is an absence claim — but nobody wrote either sentence down, because the output was a *cancellation*, not a report. Every prescription in items 1–15 triggers on writing something; this one produced nothing to check. So extend the habit past reporting: **when an action's purpose is to make a set empty — clearing a queue, killing processes, deleting temp files, revoking keys — re-enumerate the set afterward and confirm it is empty, rather than trusting that the items you acted on were all the items.** And note the second failure riding along: having wrongly concluded the queue was clear, the worker escalated to a much more exotic hypothesis (the runner is down) and burned effort on an endpoint it lacked permission to read. **A false "I've ruled that out" does not merely fail to help — it redirects the investigation somewhere stranger**, which is case 1's negative-result trap arriving one layer up.

    **The fifth instance finally produced the mechanical defense, and it is the most useful line in this entry.** Verifying the shipped fix, the worker compared anchor counts before and after and found **48 more had disappeared than its own issue predicted**. That delta is what exposed the count: the codes were `CharField`, so rows holding an **empty string** rendered as `COMP_CD=` with no `None` anywhere — invisible to the `=None` grep that both the steward and then the worker had run. Real broken links, 87 not 39, and no amount of re-reading either report would have shown it. Two things to take:

    **(a) Check by delta, not by absolute count.** An absolute number can only be compared against your own expectation, which came from the same flawed predicate — so it agrees with itself. A before/after delta is generated by the *system*, not by your query, and a mismatch between "what I predicted would change" and "what actually changed" surfaces predicate errors you do not know you made. This is the one technique in this file that catches a wrong predicate *without* requiring you to suspect it.

    **(b) Write the defense to the type, not to the grep.** The fix survived the bad number only because it was written as `{% if code %}` — absorbing null and empty string together because a `CharField` permits both — and locked with tests over `[None, '']`. Had it been built to the measured cases (`{% if code != 'None' %}`), 48 sites would still be broken. **Derive the guard's coverage from the value set the type admits, not from the count of instances you found.** Enumeration tells you the bug exists; the schema tells you how wide the guard must be. See [[relayed-numbers-carry-decomposition]].

    **A sixth instance, hours later, showed that (a) has a weaker and a stronger form — and the weaker one still passes while wrong.** Preparing the same release, the worker checked its delta and found files `29 → 31`; it had expected `+3`. Counting alone would have read `+2` as close enough. Taking the *set difference* instead showed which files actually moved, and the missing one was the finding: the earlier fix had changed a **template tag**, not the template everyone had been saying it changed. So: **counting the delta and itemizing the delta are different acts, and only the second can tell you the delta is made of what you think.** A matching number is agreement between two summaries; a matching itemization is agreement about the world. The same distinction decided the release's other check — a restored changelog section was verified not by heading *count* (which answers "how many", never "in the right place, byte for byte") but by diffing the entire tail against the previous tag until it came back empty. **Prefer the comparison that uses no predicate at all**: a whole-artifact diff cannot undercount, because there is nothing in it to get narrow.

    **What that release then demonstrated is that this technique does not transfer between media on its own.** Hours after verifying the changelog by whole-file diff rather than by heading count, the same worker verified the deployed *page* with five indicators — HTTP status, `None` occurrences, empty-parameter queries, row count, anchor count — and stopped there. The steward instead diffed the fetched HTML against a capture saved earlier and got byte-for-byte identity, which is the stronger claim and the one that actually fit the situation (a version-bump commit *should* change nothing). The worker's own reading is the durable part: *"지표 5개로 봤는데 그건 내가 볼 줄 아는 것만 본다"* — **an indicator set can only report on the failure modes you already thought of, so it is structurally incapable of surprising you**, which is the entire job of a verification. It had the better method in hand that same day and did not carry it across, because the two artifacts did not look alike. So when you adopt a checking technique, ask immediately where *else* today's work has a before-state you could diff against; a method is learned when it survives a change of medium, not when it works once. And keep the accompanying reframe: **39 was not a wrong number, it was a narrow-predicate number** — its 48 missing cases were spelled differently and would never have appeared under that grep no matter how carefully it was re-run. Distinguishing *miscounted* from *counted something else* decides whether the fix is more care or a different instrument.

    **And the same afternoon supplied the cheapest catch of all: verifying the convention caught an instruction error nobody was auditing.** A steward dispatch specified citing `#1138` in the changelog. The worker did not check that number — it checked whether the repo's convention cited *issues or PRs*, classifying the five existing references, and the convention said issues; `#1138` was the PR closing issue `#1137`. The wrong number fell out of a question aimed elsewhere. Its own account: *"관례를 확인한 게 지시를 검산한 셈이 됐습니다."* This is the second time that day a worker corrected a steward-supplied figure by re-deriving rather than transcribing. **Establish that not transcribing a number handed down from above is the expected behavior, not insubordination** — authority flows down, but verification has to flow both ways, and an unchecked figure from a superior travels further than one from a peer precisely because nobody expects to check it. See [[relayed-numbers-carry-decomposition]] and [[relayed-authority-cannot-self-certify]].

    **The release closed the loop by producing the mirror image of the morning's error, and the pair is the durable lesson.** Verifying the production deploy, the worker had every reason to skip the display layer: production's data left no visible defect, so the fix "had nothing to change there." It compared the stripped visible text file-for-file anyway — and found **one character different out of 6,594**. A company's prior-year rank had gone from `0` to `-`, because Django's `default` filter fires on all falsy values, not just null. The issue and release notes said *"null → dash"* throughout; the code shipped *"empty → dash."* **All six indicators passed. Only the whole-file comparison caught it.**

    Set beside the morning's miscount, the shape completes: there, **the predicate was narrower than the claim** (a `=None` grep sold as "any broken link"); here, **the implementation was wider than its description**. Opposite directions, one disease — *the author's own words and the author's own code disagreed, and the author was the last to see it*, because both were written by the same understanding and so felt consistent from inside. Neither is reachable by rereading either artifact alone; both surface only when something outside your description generates the comparison. So when you write the sentence that describes what you built, **name the mechanism, not your intent for it** — "matches everything falsy" is checkable against the code, "handles missing values" is not. And note which way the error runs before reacting: a too-narrow predicate leaves defects unfixed, while a too-wide implementation changes things you never announced. Here the wider behavior turned out to be *more* correct (rank zero does not exist, so the dash tells the truth the `0` did not) — but that was established by opening the template and confirming the filter sat on exactly one field, and specifically *not* on the neighboring column where zero is legitimate. **A side effect you can argue is beneficial is still a side effect you did not predict; verify its blast radius before you keep it.**

9. **List the files a deliverable contains before certifying the deliverable.** A "script", a "PR", a "config change" is routinely several artifacts wearing one noun, and reviewing any of them produces the feeling of having reviewed *it*. Name them, then say which ones you opened. Catching real defects in one file is not evidence about the others — it is the thing most likely to make you stop looking.
10. **A safety assurance is a promise, not a summary — hold it to a different bar.** "Read-only", "no DDL", "non-destructive", "reversible" are the sentences that make a human press enter, and they travel further than you do: through a relay, into a briefing, out of your reach. Before writing one, open every file that will actually execute and read the statements themselves. "Low probability" is a legitimate finding; it is not a synonym for the promise, and only one of the two belongs in the sentence you hand someone.

11. **Never claim absence from a capped query.** `head`, `-m`, `--max-count`, `| head -20`, a paging API's first page, a UI's first screen — all of them answer "here are some matches", never "here are all of them". Before writing *no X exists*, either drop the cap, run `wc -l`, or say the cap was hit. And treat a result count that exactly equals your limit as a red flag rather than a tidy number: that is the tool's edge showing, and the thing you are looking for is disproportionately likely to be just past it, since caps truncate the tail and unfamiliar paths sort late.

12. **Before believing a zero, prove the query can return non-zero.** An empty result is the one shape where "the world is empty" and "my instrument is broken" are indistinguishable — case 11's cap at least leaves a fingerprint, and this leaves none. It also delivers you straight to an absence claim, the strongest thing you can assert and the cheapest to falsify. So give the search a positive control: point the same pattern at a case you *know* is present, or re-run it a structurally different way, before writing *no X exists*. Watch multiline forms especially — `grep -P` cannot cross a newline without `-z`, and real code wraps its arguments. This is the control group you would demand of any experiment, in search form: see [[a-test-that-cannot-fail-is-not-evidence]]. Requiring it of someone else's harness and skipping it for your own grep, in the same investigation, is the characteristic failure.

13. **For any reflection-type work, open the surface that consumes the data — once, with your eyes.** Loading data, running a migration, changing a config, seeding a catalog: the DoD must include *rendering the thing that reads it*, not only reading the data back. Verifying storage proves storage. It says nothing about the consumer, and the consumer is where users live. Ask specifically: **what breaks if a field is null, empty, or absent for some rows?** — reflection work characteristically introduces rows shaped unlike the ones already there (new entrants with no prior value, backfills with gaps), and those are exactly the rows the existing code has never seen. Note that this failure is invisible to every technique in items 1–12: the looking was complete and the data was correct. The only fix is to *cross the layer*.

    Two corollaries, because the obvious lessons here are both wrong. **(a) "Validate the data harder" cannot work when the value is legitimately absent.** A missing prior-year rank for a genuine new entrant is correct data; every data-side check passes, correctly, forever. If the anomaly is valid, the data layer has nothing to report and only the consumer can fail. **(b) Filtering the awkward rows out is a false fix.** When a queryset filter looks like the missing guard, check what disappears if you add it — dropping the row buys a green page by deleting a real record from the user's view. Null the consumer must tolerate is not contamination to be screened; make the consumer robust, not the data uniform.

14. **When a verification gap turns up, re-check what you previously concluded on top of that verification.** The finding is rarely just a bug. This worker's "staging reflects correctly" had already become "DoD1 is possible without a release" in a decision document in front of a human — one sentence, load-bearing, and false for precisely the reason just discovered. So after any "we did not actually check X", trace forward: what did we assert *because* X looked fine? And when you correct such a sentence, **annotate it rather than delete it** — the reasoning is what gets reused, so why it was wrong has to survive alongside the correction. See [[verify-the-citations-you-hand-down]] on right-conclusion-wrong-grounds.

15. **Having opened the surface, also machine-read what it produced — and never write an unmeasured value into a Definition of Done.** Item 13 gets you to the consumer; this keeps you from stopping one layer short of the truth. A screenshot proves what a human sees, which is a *sample* of what the surface emits: `href`s, data attributes, form values, and downstream payloads all render invisibly, and a link whose text is a tidy `-` can carry `?id=None` into someone else's system. So after looking, fetch the artifact and count — `grep -c` the sentinel (`None`, `NaN`, `undefined`, `null`), check tag balance, diff against a row you know is healthy. These are mechanical, and they see precisely what eyes cannot. **Count on the raw bytes, not through a parser**: a browser DOM reports 200:201 where `curl` reports 200:1, because the parser silently repairs malformed markup and hands you the recovered tree. For structural defects the friendlier instrument is the blind one — read what was *served*, not what something managed to salvage. And when you count with a filter, **name the predicate you actually ran, not the one you meant** — `kiscd=None` is not "any None href", and the difference was five rows that a fix would have missed. Two amplifiers: **the malformed output is disproportionately in the template you just edited**, so look there first; and **any value you state in the pass criteria must be measured, not inferred from reading the code** — an inference in a report misleads once, but an inference in a DoD becomes the yardstick and certifies the wrong thing every time it is used. Write *expected (unverified)* beside it, or go measure it before it becomes a standard.

16. **When the question is about a remote system, ask the remote system — not your local cache of it.** Many everyday commands answer a *cached* question while reading like they answer the live one. `git branch -r --contains X` does not mean "is X on a remote"; it means "is X on a remote **as my local refs last remembered them**" — and those refs go stale the moment anyone else pushes, or the moment you skip a fetch. `git ls-remote` asks the server. The same split runs everywhere: a package lockfile vs the registry, a cached DNS answer vs an authoritative lookup, a `--dry-run` plan built from stale state vs the state at apply time, an ORM's identity map vs the row, a CDN response vs the origin. **Both commands succeed, both print something confident, and only one of them was on the network.** The tell is that the cached form is faster and needs no credentials — convenience is the symptom, not a feature.

    This is the sharpest instance because it can fail in *both* directions and the two failures look nothing alike. A false "it's missing" costs someone work they did not need to do; a false "it's already there" **loses the thing you were trying to save** — and it fails silently, at the exact moment you stop worrying. So when the claim is *absence from a remote*, the standard is: query the remote, and if the point is to preserve something, **re-query after writing** to confirm the write landed (see [[surface-vs-delivered]] — pushing and having-pushed are different facts).

    Recorded because the steward made exactly this error on 2026-08-10 while spending the whole day catching narrower-than-claimed predicates in other people's work — claiming three commits existed nowhere but one disk, when two were already safely on their remotes and only one really was at risk. The correction came from a worker that had used `ls-remote` before *and* after its push. **Being the one who names the pattern confers no immunity from it**; if anything it supplies the confidence that skips the check. The general form: *a verification habit you apply to others' claims is not yet a habit until it survives contact with your own.*

17. **A regression claim has two observations in it, and the older one is the one you did not check.** "It worked on Monday, it fails now" feels like a single fact, but it asserts that the *only* thing that changed is the thing you are investigating. The earlier success has its own scope — which account, which profile, which flag, which branch, which cached credential — and it is the half nobody re-examines, because it already produced the reassuring result. So before reporting a regression, state the conditions of the **baseline** as explicitly as the conditions of the failure, and confirm they differ in exactly one place. A "before" you cannot pin down is not a baseline; it is a memory.

    On 2026-08-10 a worker flagged that a profile which could query CloudFormation on 08-03 now got AccessDenied on every call — a credible permission-reduction signal, correctly escalated. The investigation killed it: the role had *never* held `cloudformation:` permissions in any commit, and the worker's own 08-04 notes already recorded exactly that. The earlier successes had been run under a different, admin profile. **Nothing regressed; the two halves of the comparison were never the same experiment.** Note the shape — this error survives careful work, because the failing half was measured precisely (identity confirmed via `sts get-caller-identity`, error confirmed as genuine rather than an expired token) while the passing half was recalled.

    Two practical consequences. First, this is the cheapest false alarm to manufacture and one of the more expensive to chase, so the baseline check belongs *before* the escalation, not after. Second, a worker that dismantles its own reported signal — as this one did, by exhausting hypotheses rather than gathering support for the one it started with — is doing the harder and more valuable thing; say so, or the incentive quietly becomes to let plausible alarms stand.

18. **An identity field tells you which credential acted, never which agent did.** `merged_by`, `author`, `committer`, `user.login`, an audit log's actor column — every one of them records *the account the action was performed under*. In any setup where more than one actor shares an account, the field is structurally incapable of answering "who did this": a fleet of agents operating under the owner's authenticated session produces records byte-identical to the owner acting personally. This is not a gap you can close by looking harder at the record; the information was never captured. So before writing *"the owner approved it"* or *"a human reviewed this"*, ask what would look **different** if the other actor had done it — and if the answer is "nothing", you have an account, not an actor, and you must say so or go ask a person.

    The trap is that this failure wears the costume of hard evidence. On 2026-08-10 the steward told a worker its release condition — *"the owner, or someone with real review authority, merges it directly"* — had been satisfied, citing `merged_by: <owner>` on three merged PRs. The worker refused the conclusion and named the reason: every agent in this fleet commits under the owner's identity, so an agent running `gh pr merge` yields exactly that record. Checking further **strengthened the worker**: all three PRs had **zero approving reviews**, and the commit asserting the merges also asserted a "routing principle" waiving approval — in the same breath as a claim already proven false. The steward had spent that entire day catching narrow predicates in others' work and still read an account-level signal as a human act.

    Two follow-ons. **When one claim from a source is disproven, the source's remaining claims do not keep their prior standing** — they revert to unverified, and inheriting them for free is how a single fabrication launders a whole document. And **a subordinate who refutes a superior's stated conclusion with evidence is doing the most valuable thing available to them**; if that had gone unchallenged, a false release fact would have been written into the permanent ledger by the very worker it deceived. Say so out loud when it happens, or the incentive quietly inverts.

19. **A correction you hand *down* needs more verification than a claim you make, not less.** Ordinary claims get tested by whoever receives them. A superior's correction is different: the subordinate usually accepts it, it overwrites a report that was already precise, and it then propagates — into escalations, ledgers, and decision documents — carrying the authority of the role rather than the strength of its evidence. **The correction is the one assertion in the system least likely to be checked by anyone else,** so it has to be checked by you, at the moment it feels most obviously right.

    On 2026-08-10 a worker reported that a security fix had been merged **to `main`**. The steward "corrected" it to `devel`, on the sole ground that `gh api repos/... --jq .default_branch` returned `devel` — and relayed that corrected, weaker picture to the human. But a default branch says nothing about how many branches exist or how promotion flows; this repo runs `devel → staging → main`, which is entirely consistent with `default_branch: devel`. The worker had been exactly right. It re-measured, pushed back with the gate function present on all three branches and absent from the running release tag, and named why the distinction mattered: *"devel only"* implies a multi-stage promotion chain, while the truth was **one release publish** — a different workload, review burden, and rollback cost. The human had been handed options built on the steward's error, one of which ("split out just the security fix") was rendered meaningless by the facts.

    Note the asymmetry that makes this worth its own item: the worker's statement was a **measurement**, the steward's correction was an **inference from a weaker fact** — and the inference won purely on rank. Two rules follow. **Before overriding a subordinate's specific factual claim, verify at the same resolution they did**; "I know a general thing about this system" does not outrank "I looked at this specific thing". And **a correction is only complete when it says what the corrected fact changes for the decision** — this worker's real contribution was not "you got the branch wrong" but "and here is how the options differ", which is what makes a correction usable rather than merely accurate. See [[verify-delivery]]: the reader must be able to fix their own judgment, not just observe that someone was wrong.

20. **A session's failure is a fact about that session's environment, not about the repository.** "I couldn't build the evidence" and "the evidence cannot be built here" are different claims, and the gap between them is *whose machine you were standing on*. A fresh session, a container without a warm venv, a reviewer that never ran the project — each can hit a wall that the authoring session walks straight through. Before promoting a tooling failure into a property of the repo, ask **which session hit it, and does another session already have what it lacked?**

    On 2026-08-13 the steward escalated to 정수님 that the standing merge rule's coverage condition was **structurally unproducible** in two of three repos, tabling `dealmatch` as "불가" because the reviewer session hit a private-index `401` on `uv sync`. **Five minutes later the authoring session produced it** — coverage∩diff plus revert-verify across all six defensive branches — because that session had a working environment all along. The reviewer's report was accurate and precisely scoped; **the false claim was manufactured entirely by the steward's generalization of it.** Had the escalation been acted on, a standing quality bar would have been relaxed to accommodate a problem that did not exist in two of the three cases cited.

    Note what survived the correction and what did not. `chat-proxy` really is structurally blocked — no diff-coverage tooling exists in the repo at all, so **no session can produce it** — and that half stood. So the discipline is not "distrust the report" but **partition by cause before generalizing**: a *missing tool in the repo* generalizes across sessions, a *missing environment in one session* does not. Two failures that render identically at the point of observation ("condition 1 not produced") have opposite scopes, and only opening the cause distinguishes them.

    The aggravating factor is the destination. This was not an analysis but an **escalation asking a human to change a standing rule**, which is [[an-unverified-constraint-spends-the-humans-hand]] — the one document class where a wrong premise converts directly into a permanently lowered bar. Escalations that propose relaxing a standard need their *motivating* facts verified at the same bar as the standard itself. And the correction had to **replace** the original rather than sit beside it ([[a-correction-must-replace-not-append]]); a queued decision carrying a superseded table is worse than no decision, because the reader cannot tell which half to act on.

**SPT:** the habit is *before acting on "it's not X" or "there's no Y," say what you actually looked at — and check the conclusion fits inside it.*
