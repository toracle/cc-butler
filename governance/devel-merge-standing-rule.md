개발 브랜치(devel 등 개발 통합 브랜치 대상) 병합은 다음 네 조건이 **모두 실행된 경우에 한해** 스튜어드 재량으로 한다. 건별로 정수님께 여쭙지 않는다. **적용 범위는 jarvice 한 곳이 아니라 함대가 다루는 관련 리포 전체다**(chat-proxy, monocle, monocle-tool-server, stark, dealmatch 등 — 정수님 명시, 2026-08-11: "we should consider related/matching repos too, not only jarvice").

1. **자동 테스트 통과 — 단, 변경분이 코드 커버리지로 커버되는지 확인할 것.** 테스트가 그냥 초록인 것과 변경된 코드를 실제로 지나가는 것은 다르다. 실질 기준: 전체 % 가 아니라 **그 PR이 바꾼 라인이 실제로 실행되는가** (보안 수정이면 새 거부 분기가 실행되는가, 동시성 수정이면 락 없으면 실패/있으면 통과하는 테스트가 있는가).
2. **코드 리뷰 수행 + 리뷰 결과를 해당 PR에 코멘트로 게시할 것.** "게시했다고 믿는 것"과 "실제 게시된 것"은 다르다 — 게시 결과를 눈으로 확인한다 (#1467에서 `@경로` 문법 오용으로 경로 문자열만 올라간 실사고 있음).
3. **BDD 시나리오가 필요한 경우는 BDD 시나리오를 활용하고, 기타는 Verify-First로 점검할 것.**
4. **탐색적 테스팅(exploratory testing)으로 잠재 버그가 없는지 확인할 것.**

(+) 스튜어드 추가 조건(정수님 규칙 원문에는 없음, 이견 없어 유지 중): **독립성** — 병합 근거가 되는 리뷰를 PR 작성 세션 자신이 만들지 않는다.

**Why:** 2026-08-11, jarvice PR 8건 병합 승인 대기를 계기로 스튜어드가 "건별 승인 vs 상설 규칙"을 상신했고 정수님이 상설 규칙을 택하셨다. 축어: "풀 리퀘스트의 각각에 대해서 개별 승인하는 것보다는 상설 규칙을 하나 드리겠습니다. 그래서 자동 테스트를 통과한 개발 브랜치 그런데 그 테스트는 코드 커버리지로 커버되는 것 확인해야 합니다. 그리고 코드 리뷰를 하고 코드 리뷰 결과를 PR 커멘트에다가 추가합니다. PDD 시나리오가 필요한 경우는 PDD 시나리오를 활용하고 기타 Verify First를 사용해서 점검합니다. 익스플로러토리 테스팅으로 잠재적인 버그가 없는지 확인합니다. 거기까지 한 내용은 거기까지 실행된 개발 브랜치의 병합은 스튜어드의 재량으로 하겠습니다." ("PDD"는 BDD의 전사 오류 — jarvice에 pytest-bdd·.feature 파일 실재로 측정 확인.) 범위 확장은 같은 날 후속 지시.

## 조건 1의 증거 형태 — **확정 표준** (2026-08-11, jarvice#1684 파일럿에서 확립)

"커버리지로 커버됨"을 무엇으로 보일 것인가는 이 규칙의 실질이다. `monocle-security`가 #1684에서
제시한 형태를 **함대 표준으로 확정**했다. 네 겹이고, 어느 하나도 단독으로는 부족하다.

1. **추가 실행라인 ∩ `executed_lines` 기계 대조.** "커버됐다"를 눈으로 주장하지 말고 기계로
   대조한다. 전체 커버리지 %는 **받지 않는다** — 그 PR이 바꾼 라인의 실행 여부만이 증거다.
2. **revert-verify — 이것이 진짜 증거다.** 커버리지는 *"그 줄이 실행됐다"* 만 말하고
   *"그 줄이 없으면 실패한다"* 는 말하지 않는다. 수정을 되돌리면 red, 적용하면 green임을 보인다.
   ([[a-test-that-cannot-fail-is-not-evidence]])
3. **CI가 그 파일을 실제로 실행하는지 워크플로에서 확인.** `--ignore` 목록에 없는지,
   `continue-on-error`/`|| true`가 없는지까지 본다. "CI 초록"이 *무엇의* 초록인지를 닫는다.
   ([[name-the-command-a-check-that-resembles-the-gate-is-not-the-gate]])
4. **`origin/devel` 대조로 기존 실패와 신규 실패를 가른다.** 이게 없으면 무관한 환경 실패가
   PR 탓으로 걸린다. (#1684에서 psycopg2 connection refused가 devel에서도 동일 → 회귀 아님으로 판정.)

**순서 규칙 — 본문을 읽기 전에 독립 수치를 먼저 얻는다.** PR 본문의 숫자를 먼저 읽으면 거기에
닻이 내려 검증이 아니라 **확인**이 된다. #1684 리뷰어는 수치를 독립적으로 먼저 얻은 뒤 본문과
대조해 일치를 확인했고, 그래서 그 일치가 의미를 가졌다.

**증명할 수 없는 것을 증명한 척하지 않는다.** red-before-green의 *순서*는 사후 증명 불가다.
보일 수 있는 것은 *"테스트가 이 수정을 판별한다"* 뿐이며, 코멘트에도 그렇게 쓴다.

**전체 스위트를 못 돌렸으면 그렇다고 쓴다.** #1684에서 실제 postgres가 없어 전체 스위트를
재현하지 못했고, 리뷰어는 그것을 감추지 않고 대체 수단(관련 파일 서브셋 devel 대조 + CI 워크플로
확인)을 명시했다. **인가(authorization) 수정은 거부 분기가 대개 DB 뒤에 있어 이 대체 수단이
하필 제일 필요한 곳에서 제일 약하다** — 그런 PR에서는 신선한 일회용 postgres를 띄운다.
⚠️ 오래 쓴 공용 테스트 컨테이너는 잔여 상태가 결함을 가리므로 **반드시 일회용·신선한 것**으로
한다 ([[steward-shared-test-container-contamination]]).

**리뷰어의 코드 수정 경계.** 인용·줄번호 정정까지는 독립 리뷰어가 직접 고쳐도 되고, 고친 사실을
코멘트에 밝힌다. 그 이상(로직·테스트·계약)은 작성자에게 돌려보낸다 — 리뷰어가 코드를 만지기
시작하면 독립 리뷰어가 아니라 **공저자**가 된다.

**PR 본문이 틀린 채로 병합하지 않는다.** 본문은 나중에 판단하는 사람이 읽는 **유일한 요약**이고,
틀린 요약은 틀린 코드보다 멀리 간다. 같은 날 jarvice#1664의 본문이 *"cdk 단계에서 인프라 변경이
함께 적용됨"* 이라 적었으나 워크플로에 cdk가 아예 없었고, 그 본문만 읽고 프로덕션 태그를 끊었으면
인프라가 같이 나간다고 믿은 채 끊었을 것이다 ([[a-pr-body-states-intent-verify-the-closure]]).

## ⚠️ 조건 1의 "CI 초록"은 **플랫폼이 아니라 스튜어드가 강제한다** (2026-08-11 측정)

이 규칙을 읽으면 "CI가 초록이어야 병합된다"가 **기계적으로 보장된다**고 읽히기 쉽다. **그렇지 않다.**
2026-08-11 실측:

| 저장소 | 브랜치 | 브랜치 보호 | rulesets |
|---|---|---|---|
| jarvice | devel(기본), main | **없음** (`404 Branch not protected`) | `[]` |
| monocle | main | **없음** | `[]` |
| stark | devel, main | **없음** | 2건 — 단 `prevent to create main branch` / `protect from deletion`, **구조 보호이고 필수 상태 검사 아님** |

조직 플랜은 **Team**이라 프라이빗 저장소에도 켤 수 있다 — **못 켜는 게 아니라 안 켜져 있다.**
그리고 stark가 rulesets를 이미 쓰고 있다는 것은 방법을 몰라서가 아니라 **CI 강제만 선택적으로
걸지 않은 상태**라는 뜻이다(jarvice의 `.disabled` 워크플로 5개와 같은 결). 그래서 이것을
**결함으로 단정하지 않는다** — 의도된 설정일 수 있고, 판단은 정수님 몫으로 상신되어 있다.

**따라서 지금 red 병합을 막는 것은 GitHub가 아니라 병합 직전 스튜어드의 손 확인뿐이다.**
2026-08-11 밤 devel 병합 4건(#1684·#1467·#1685·#1693) 전부 병합 직전 `gh`로 체크 상태를 직접
조회해 확인했고 실제로 전부 초록이었다 — **사고는 없었다. 문제는 결과가 아니라 구조다:**
그 확인이 규칙이 아니라 **한 세션의 습관**에 걸려 있고, 습관은 그 세션이 압축·교체되면 함께 사라진다.

**적용:**
- **병합 버튼을 누르기 전 체크 상태를 직접 조회한다.** 워커가 보고한 "CI 초록"을 그대로 받지 않는다
  — 보고 시점과 병합 시점 사이에 devel이 움직였을 수 있고, 무엇보다 **플랫폼이 되받아주지 않는다.**
  `mergeable`이 `UNKNOWN`이면 GitHub 계산을 기다렸다 재조회한다. UNKNOWN 상태로 누르지 않는다.
- **병합 후 devel의 CI도 확인한다.** 보호가 없으면 병합 결과가 devel을 red로 남겨도 아무도 안 막는다.
- 이 절은 **브랜치 보호가 켜지면 반드시 다시 쓴다.** 켜지더라도 관리자 우회를 허용하는 형태(권고안)면
  강제는 **부분적**이므로 "이제 플랫폼이 막아준다"로 바꿔 쓰면 안 된다.

**How to apply:** (a) 네 조건(+독립성)이 실제로 실행됐는지 스튜어드가 PR별로 확인한 뒤에만 재량 병합한다 — 미충족 PR은 조건을 채우거나 정수님께 올린다. (b) 개발 통합 브랜치 병합에만 적용된다. 프로덕션 배포·릴리스 태그·실과금·비가역 변경은 여전히 정수님께. (c) 기존 대기분에도 소급 면제 없이 적용한다. (d) 관련 리포 전체에서 병합 대기 상태의 PR을 같은 기준으로 감사한다. (e) 조건 1은 위 "확정 표준" 네 겹으로 판정한다. 관련: [[merge-verification-bar]], [[evaluation-independence]], [[reversibility-is-the-escalation-test]].
